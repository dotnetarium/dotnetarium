# DNA0022: Embedded provider credential

Reports recognizable provider secret credentials embedded in configuration files. Detection is offline by default. Both integrations use distinctive secret prefixes or provider-specific context; the CLI also checks classic GitHub token checksums and can optionally verify GitHub credentials with GitHub.com. Format or checksum matches alone do not establish whether a credential is active, expired, revoked or synthetic.

## Supported formats

### GitHub

| Credential | Format |
| --- | --- |
| Personal access token | `ghp_` + 36 ASCII alphanumeric characters |
| OAuth token | `gho_` + 36 ASCII alphanumeric characters |
| App user token | `ghu_` + 36 ASCII alphanumeric characters |
| App installation token | `ghs_` + 36 ASCII alphanumeric characters |
| Stateless app installation token | `ghs_APPID_JWT`, with a bounded app identifier and three base64url JWT segments |
| App refresh token | `ghr_` + 36 ASCII alphanumeric characters |
| Fine-grained personal access token | `github_pat_` + 82 ASCII letters, digits or underscores |

Complete boundaries are required; wrong lengths, obvious repeated-character placeholders and bodies containing EXAMPLE or PLACEHOLDER are ignored. Public repository URLs, user/app IDs, public keys and references such as `${{ secrets.GITHUB_TOKEN }}` are not findings.

These are the catalogued formats, not every historical or future token variant. Synthetic tokens with realistic format can still be reported. Stateless token recognition requires a JSON-shaped `eyJ` header, an alphanumeric app identifier of at most 32 characters, and bounded header/payload/signature segments (2,048/8,192/2,048 characters). It does not decode claims or validate signatures.

### Cloud and infrastructure

| Provider | Supported secrets | Required pattern/context |
| --- | --- | --- |
| AWS | Secret access key | Literal `aws_secret_access_key` assignment, case insensitive, followed by 40 ASCII letters/digits or `/+=` |
| Azure Storage | Account key | `AccountName` and `AccountKey` in the same connection string; Base64 encoding of 64 bytes |
| Azure Cosmos DB | Account key | HTTPS `AccountEndpoint` under `documents.azure.com` and `AccountKey` in the same connection string; Base64 encoding of 64 bytes |
| Azure Service Bus / Event Hubs | Shared access key | `Endpoint=sb://...servicebus.windows.net` and `SharedAccessKey` in the same connection string; Base64 encoding of 32 bytes |
| Azure Storage | SAS signature | Azure `blob/queue/table/file.core.windows.net` HTTPS URL with `sv`, `sr` or `ss`, `sp` or `si`, and a `sig` encoding 32 bytes |
| Google Cloud | Service-account private key | JSON root `type: service_account` with a complete PKCS#8 PEM `private_key`, decodable Base64 and DER sequence header |
| Google OAuth | Access token | `ya29.` followed by 30–2,048 ASCII letters/digits, underscores, hyphens or dots; final character is not a dot |
| DigitalOcean | Personal, OAuth access and refresh tokens | `dop_v1_`, `doo_v1_`, `dor_v1_` + 64 lowercase hexadecimal characters |
| HashiCorp Vault | Service, batch and recovery tokens | `hvs.`, `hvb.`, `hvr.` + ASCII letters/digits, underscores or hyphens; 24–256 characters for service/recovery, 24–2,048 for batch |
| Terraform Cloud | API token | 14 ASCII letters/digits + `.atlasv1.` + 60–70 ASCII letters/digits, `_`, `-` or `=` |
| GitLab | Personal access token | `glpat-` + 20 ASCII letters/digits/underscore/hyphen, or routable form with 27–300 characters + `.` + 9 lowercase letters/digits |
| GitLab | Deploy, OAuth application and Kubernetes agent tokens | `gldt-` + 20, `gloas-` + 64, `glagent-` + 50 ASCII letters/digits/underscore/hyphen |

Diagnostics point at the secret value rather than its field name or the whole connection string. GCP private-key locations cover the JSON string content, including escaped newlines. Service-account detection parses JSON and checks key material shape; the analyzer does not validate an RSA key or authenticate the account, while the CLI additionally imports the RSA key offline. Azure SAS signatures support URL encoding and XML `&amp;` separators. Azure connection strings are checked within a single physical line, with flexible property order and spacing. Separate quoted connection strings cannot supply context to each other.

The documented public Azurite emulator key is excluded by exact value. A development-looking account name alone does not suppress a real key. AWS `AKIA`/`ASIA` access-key IDs, Azure tenant/client/subscription IDs and instrumentation keys, Google client/private-key IDs, public PEM keys and GitLab feature-flag client tokens are not secret findings. Google `AIza` API keys are deliberately excluded: usage and restrictions determine their risk, so the prefix alone does not meet this rule's credential policy.

This slice does not detect unprefixed generic client secrets, AWS session tokens, old Vault `s.`/`b.`/`r.` forms, standalone Azure SAS strings, arbitrary-host signed URLs, GCP private keys in YAML or sovereign-cloud Cosmos/messaging/SAS endpoints. It does not reconstruct split connection strings. Provider token formats are versioned and opaque; bounded recognition covers these documented or catalogued forms, not every future variant. Realistically shaped synthetic fixtures may still be reported.

Provider references: [AWS access-key components](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html), [Azure Storage keys](https://learn.microsoft.com/en-us/azure/storage/common/storage-account-keys-manage), [Azure connection strings and SAS](https://learn.microsoft.com/en-us/azure/storage/common/storage-configure-connection-string), [Azure messaging keys](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-sas), [Google service-account key files](https://docs.cloud.google.com/iam/docs/keys-create-delete), [Google OAuth REST authentication](https://docs.cloud.google.com/docs/authentication/rest), [DigitalOcean token prefixes](https://docs.digitalocean.com/products/droplets/reference/api/droplets/), [Vault token prefixes](https://developer.hashicorp.com/vault/docs/concepts/tokens), [GitLab token types](https://docs.gitlab.com/security/tokens/). ## CLI checksum checks

For 40-character `ghp_`, `gho_`, `ghu_`, legacy `ghs_` and `ghr_` tokens, the CLI checks the last six characters against the CRC32 of the preceding 30-character token body, encoded as zero-padded base62 (`0-9A-Za-z`). Checksum mismatches are omitted. Checks occur during scanning, before findings enter diagnostics or output; the token is not attached to diagnostic properties.

Fine-grained PATs and stateless installation tokens have different layouts and remain format-only findings. No checksum is guessed for those layouts. A passing checksum confirms structural consistency, not that GitHub issued the token or that it is active. The NuGet analyzer continues to report format matches, including checksum-invalid realistic fixtures.

The CLI also validates the current versioned GitLab routable PAT: `glpat-<payload>.01.<length><crc32>`. It checks the two-character base36 payload length and seven-character base36 CRC32 over the entire encoded token before the checksum. Mismatches are omitted. Legacy layouts and unknown future versions remain format matches. The analyzer reports format matches without checksum checks. [Official format and generator](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/cells/routable_tokens/).

For GCP service-account JSON, the CLI imports the PKCS#8 RSA key to reject malformed DER fixtures. This is offline structural validation, not account or key liveness verification.

## File scope

The CLI scans recognized config files under the nearest containing Git repository root, including `.github` even when the solution is in `src/`. A `.git` file identifying a worktree is supported. Without Git, scope is the solution/project directory. Participating project directories outside that root are scanned too. C# project selection still follows the supplied solution/project.

Supported inputs: JSON, YAML, TOML, INI, `.config`, `.env` and `.env.*`, `.npmrc`, project/build XML (`.csproj`, `.props`, `.targets`, `.pubxml`), Terraform `.tf`, `.tfvars`, `.hcl`, `.tfrc`, `.terraformrc`, and `.aws/credentials` below the existing scan root. The CLI does not scan the user's home credentials unless they are in scope or explicitly supplied as project inputs. Files are scanned as text, including commented credentials. Escaped or split/concatenated tokens are not generally reconstructed; GCP service-account JSON and Azure SAS URL encoding are the exceptions described above.

CLI discovery skips `.git`, `.svn`, `.vs`, `bin`, `obj`, `node_modules`, `packages`, `artifacts`, nested Git repositories and symbolic links/junctions. Files exceeding 2 MiB are skipped with a coverage notice. The resolved root and scanned file count are printed. Config findings survive project loading/compilation failures; such failures still return exit code 2. `--fail` returns 1 for findings when scanning otherwise succeeds.

### CLI include/exclude options

Use repeatable `--config-include <glob>` and `--config-exclude <glob>` options. Matching is relative to each printed config scan root; for projects outside the main root, their project directory is a separate root. Explicit linked `AdditionalFiles` use their consuming project's scan root and can have `../` in the displayed relative path; a glob such as `**/shared.json` can select them. The filters apply to both discovered files and project `AdditionalFiles`, in project and no-build modes. Each file path is scanned once.

- No includes means all recognized config inputs. Multiple includes form a union.
- Exclusions take precedence over includes. Excluded directory subtrees can be skipped before reading files.
- `*` matches characters within a path segment, `?` matches one character, and `**` crosses directories. `**/` also matches zero directories. A trailing `/` selects the whole subtree.
- Globs use `/` or `\\` separators and optional leading `./`. Matching is case insensitive on Windows and case sensitive on Linux/macOS. Quote globs to prevent shell expansion.
- Absolute paths, parent-traversal globs, brace expansion and character classes are rejected. Options select files within the existing scan scope; they do not add directories or override discovery's built-in exclusions.

```sh
dotnetarium src/App.sln --config-include '**/*.json' --config-include '.github/**/*.yml' --config-exclude '**/fixtures/' --fail
```

These flags do not exclude C# source analysis, change solution/project selection, or prevent loading `dotnetarium.json` rules configuration. The NuGet analyzer's file scope remains controlled by MSBuild `AdditionalFiles` and `DotnetariumScanConfigFiles`.

The analyzer package automatically adds recognized configuration files below the consuming project directory as Roslyn `AdditionalFiles`, honoring SDK item exclusions and excluding dependency/build output directories. It does not discover the repository root. To include shared files explicitly:

```xml
<ItemGroup>
  <AdditionalFiles Include="../../.github/workflows/ci.yml" />
</ItemGroup>
```

To disable automatic project config inclusion, set `<DotnetariumScanConfigFiles>false</DotnetariumScanConfigFiles>`. Explicit AdditionalFiles still work. Analyzer inputs exceeding 2 MiB are skipped. Package diagnostic severity can be configured with `dotnet_diagnostic.DNA0022.severity`.

The CLI reports findings independently of `.editorconfig` suppression by default. Add `--respect-editorconfig` to honor configured rule severity and suppression. Code analysis uses the project's Roslyn configuration; independent config findings use ancestor `.editorconfig`/`.globalconfig` files and Roslyn's glob and precedence rules. This also works when project loading fails.

The NuGet analyzer performs offline format matching only. Checksum checks run in the CLI. Neither performs network verification by default. A recognizable token is not proof that the credential is currently usable.

## Verification and reduction

### Choose a scanning mode

| Mode | Command / integration | Network verification |
| --- | --- | --- |
| IDE or build | NuGet analyzer package | Never |
| Offline CLI | `dotnetarium src/App.sln --sarif findings.sarif` | Off |
| CLI with validity checks | Add `--verify-secrets` | Supported credentials or signed requests go to fixed provider endpoints |

Verification works with both project loading and `-nb`. It applies only to `DNA0022` configuration-file findings; it does not verify generic literal credentials reported by `DNA0009`.

```sh
dotnetarium src/App.sln --verify-secrets --sarif findings.sarif --fail
```

`--verify-secrets` explicitly permits credential checks against the fixed cloud endpoints below. No separate provider account, login, scanner API key, or credentials from the scanner's environment are required. Verification happens after scope and optional editorconfig suppression. The NuGet analyzer never makes network requests.

### Final supported verification list

| Credential | Check | Required context |
| --- | --- | --- |
| GitHub personal, fine-grained, OAuth and app user access token | `GET https://api.github.com/user` | Token only |
| GitHub installation token | `GET https://api.github.com/installation/repositories?per_page=1` | Token only |
| GitLab PAT, including versioned routable PAT | `GET https://gitlab.com/api/v4/personal_access_tokens/self` | Token only; GitLab.com only |
| DigitalOcean `dop_v1_` / `doo_v1_` | `GET https://api.digitalocean.com/v2/account` | Token only; missing `account:read` remains unknown |
| Terraform Cloud API token | `GET https://app.terraform.io/api/v2/account/details` | Token only; user, team and organization tokens |
| AWS long-term / temporary credential set | Signed STS `POST https://sts.amazonaws.com/`, `GetCallerIdentity` | ID and secret in the same JSON object or INI/environment section; temporary `ASIA` credentials also require session token |
| Azure Storage account key | Signed container-list GET with `maxresults=1` | Account name and key in the same connection string; public Azure host |
| Azure Cosmos DB account key | Signed database-list GET with page size 1 | HTTPS `*.documents.azure.com` endpoint and key in the same connection string |

AWS's POST is an identity lookup, not credential issuance. AWS/Azure keys are used locally to sign the request; the raw signing key is not sent. Identity acceptance does not establish broad permissions. Azure checks read metadata, not blobs or database documents; returned metadata is discarded.

AWS pairing rejects duplicate/ambiguous credential components and never combines separate JSON objects or INI profiles. It recognizes `aws_access_key_id`, `aws_secret_access_key`, and `aws_session_token` assignments; other naming conventions are left unknown. It does not execute an AWS credential chain, assume roles, or consult the user's home credentials. Azure context rejects duplicate connection fields, overridden storage endpoints and nonstandard Cosmos ports. Missing context is unknown, not a verification failure or suppressed finding.

### Explicitly outside verification scope

| Credential / operation | Behavior |
| --- | --- |
| GitHub / DigitalOcean refresh tokens | Unknown; never exchanged, refreshed or rotated |
| Vault service, batch and recovery tokens | Unknown; no lookup, login, unwrap or limited-use-token consumption |
| GCP service-account private keys | Offline RSA structure check only; no JWT exchange or access-token issuance |
| Google OAuth access tokens | Unknown; no tokeninfo request containing a credential in its URL |
| Azure Storage SAS / Service Bus / Event Hubs keys | Unknown; no blob reads, message operations or permission guessing |
| GitLab deploy / OAuth application / agent tokens | Unknown; no incorrect PAT endpoint probing |
| Self-hosted GitHub/GitLab/Terraform and sovereign-cloud endpoints | Unsupported; cloud checks do not establish validity on another host |

Repository-controlled endpoints, paths, commands and credential JSON are never executed or used as arbitrary verification destinations. No refresh, rotation, revocation, resource mutation or extra permission enumeration is performed. Normal provider requests can still generate audit events.

| Status | Meaning |
| --- | --- |
| active | The selected cloud endpoint accepted authentication and returned the expected response; no claim about broader permissions |
| inactive | The selected endpoint explicitly rejected the credential set; this is not proof of revocation or validity on another instance |
| unknown | Unsupported credential/context, rate limit, access restriction, network error, unexpected response or exhausted budget |

Azure failures remain unknown: a 401/403 can reflect clock/signing problems, firewall restrictions or disabled Shared Key authentication. GitLab 403 and Terraform 404 remain unknown. DigitalOcean's documented unauthorized response, Terraform's authentication error, GitLab.com's documented 401 response, and recognized AWS STS invalid/signature/expired-token errors produce inactive status. GitHub retains its documented `Bad credentials` handling.

Console output includes status and a safe reason. SARIF result properties are `dotnetarium.secretVerification` and `dotnetarium.secretVerificationReason`. Responses, raw credentials, account metadata and credential hashes are omitted. Each distinct credential **and bound context** is checked once within a scan, without collapsing separate occurrences. There is no persistent credential cache. Requests are sequential, redirects are disabled, and responses are capped at 64 KiB; XML DTDs/entities are prohibited. Limits are five seconds per request, thirty seconds overall and at most 64 requests. HTTP 429 stops further checks for that provider; GitHub 403 rate-limit responses do too. Verification failure does not change scan coverage or exit status. Findings in every status remain reported and count for `--fail`.

Without `--verify-secrets`, no verification status is attached and no verification credentials/context are captured. Unsupported Google/Vault credentials are not retained for network verification. All supported providers use their own endpoints; credentials are never forwarded to another provider.

### Recommended reduction policy

| Concern | NuGet analyzer | CLI |
| --- | --- | --- |
| Invalid or obvious placeholder format | Existing bounded format and placeholder checks | Same checks, plus classic-token checksum |
| Intended fixture | Prefer a conspicuous placeholder; explicit file/rule severity if necessary | Prefer a placeholder; explicit config scope or opt-in editorconfig |
| Live credential | Offline warning; no network during build or IDE analysis | Optional verification to prioritize remediation |
| Repeated credential | Keep every actionable file location | Keep every location; deduplicate verification by credential identity |
| Accepted finding / future baseline | Recommend rule + normalized relative path + credential hash, with a reason | Same identity; explicitly opt in to applying a baseline |

Location alone is insufficient for persistent suppression: line movement changes it, while replacing a credential at the same line can conceal a new leak. A credential-aware baseline would survive line shifts and detect replacement credentials. Such a baseline is a proposed follow-up, not implemented here. File exclusions and editorconfig suppression are broader controls and should remain explicit. Do not automatically trust `tests/`, `fixtures/`, documentation or a public property: real tokens can appear there, and accessibility does not make a secret safe. This rule detects secret token families, not public client identifiers.

For an intentional fixture that cannot use an obvious placeholder, a scoped `.editorconfig` section can suppress the rule:

```ini
[tests/fixtures/synthetic-token.json]
dotnet_diagnostic.DNA0022.severity = none
```

The analyzer honors this policy automatically. The CLI applies it only with `--respect-editorconfig`; otherwise the finding is reported. Alternatively, the CLI can exclude the file explicitly with `--config-exclude 'tests/fixtures/synthetic-token.json'`. Both controls suppress the entire file's matching findings, including newly introduced credentials, so use the narrowest scope and record why the fixture is intentional.

Other tools separate these concerns too: [Gitleaks documents baselines, allowlists and finding ignores](https://github.com/gitleaks/gitleaks); [TruffleHog supports verification and verified/unverified/unknown result filtering](https://github.com/trufflesecurity/trufflehog); [GitHub validity checks expose active/inactive/unknown status for prioritization](https://docs.github.com/en/code-security/concepts/secret-security/validity-checks). Our recommendation keeps offline build behavior predictable and uses verification to enrich findings without automatically discarding them.

API references: [authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user), [installation repositories](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-app-installation), [refresh-token exchanges](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens).

## Remediation and output

Remove the credential and retrieve it from a secret store or environment variable. Rotate/revoke credentials that may have been exposed. Keep deliberate fixtures as obvious placeholders instead of realistic tokens.

Diagnostics identify the provider/token kind and exact file location. Dotnetarium console/SARIF output does not embed the token or source snippets. Occurrences in different files remain separate findings; repeated discovery of the same occurrence is deduplicated.

Verification is independently implemented against the providers' documented APIs.
