# DNA0004: Untrusted file path

An application that uses an untrusted path for a file operation may let a caller read, replace or delete files outside the intended location. Archive entry names can create the same problem during extraction. A path used to load an assembly or native library can also select executable code.

For example, removing `Files/` from an archive entry named `Files/../outside.txt` still leaves a path that escapes the working directory. Combining it with a trusted directory does not establish containment.

## Recommendation

Resolve the destination against a trusted root, canonicalize it and check that the result remains inside that root before accessing the file. A string prefix check must include the directory boundary. Apply these checks to each entry when extracting files directly.

Containment does not replace authorization or protect against filesystem links and races. Keep sensitive directories and code-loading locations outside an attacker's control.

The rule reports consequential operations such as reads, writes, deletion, moves, extraction and path-based code loading. It excludes metadata checks, listing and standalone directory creation. A finding identifies an untrusted path, not proof that an allowed root has been escaped.
