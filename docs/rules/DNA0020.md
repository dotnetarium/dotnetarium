# DNA0020: TLS certificate validation bypass

CWE-295. Reports a networking certificate-validation callback that is proven to accept every certificate without validating it. Prefer the platform's default validation, a trusted development certificate, or explicit certificate validation/pinning. HTTPS with an accept-all callback does not authenticate the remote peer.

## Coverage

- `HttpClientHandler.ServerCertificateCustomValidationCallback`, including `DangerousAcceptAnyServerCertificateValidator`.
- `SslClientAuthenticationOptions.RemoteCertificateValidationCallback`, including options used by `SocketsHttpHandler`.
- `SslServerAuthenticationOptions.RemoteCertificateValidationCallback` for remote/client certificate validation.
- `ClientWebSocketOptions.RemoteCertificateValidationCallback`.
- `SslStream` constructors with `userCertificateValidationCallback`.
- `ServicePointManager.ServerCertificateValidationCallback`, for code still using this API on .NET 8/10.

The rule recognizes inline callbacks, nonvirtual source-defined methods/local functions, and local delegate variables initialized once without reassignment or `ref`/`out` escapes. Every return must be a compile-time `true`; unknown calls, getters, throws, loops, and other potentially rejecting operations prevent a finding. Reading or storing the accept-all delegate alone does not report: it must be installed on a modeled networking API. Lookalike application properties are excluded.

This is a configuration finding, not proof that a connection was made or that a TLS server requires client certificates. No diagnostic does not establish that a custom validator is secure. Partial bypasses, external validators, factories and field-stored delegates are not fully analyzed. Multicast `+=` chains are not inferred: an earlier callback may still reject by throwing, even when an appended delegate returns `true`.

## Development and intentional test cases

### Trust a development certificate

For ASP.NET Core development, first try:

```sh
dotnet dev-certs https --trust
```

Keep the normal validation callback unset. Containers and separate client processes may need the development certificate trusted in their own trust store. See Microsoft's [development certificate instructions](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-dev-certs).

### Guard development-only configuration explicitly

The rule excludes assignments or `SslStream` creation inside a branch that requires the framework's `environment.IsDevelopment()` check to succeed, or `environment.IsProduction()` to be false:

```csharp
var handler = new HttpClientHandler();
if (environment.IsDevelopment())
{
    handler.ServerCertificateCustomValidationCallback =
        HttpClientHandler.DangerousAcceptAnyServerCertificateValidator;
}
```

It also recognizes `IsDevelopment() && otherCondition`, `!IsProduction() && otherCondition`, corresponding `else` branches, stable local boolean aliases, and simple early-return/throw guards:

```csharp
if (environment.IsProduction()) return;
handler.ServerCertificateCustomValidationCallback =
    HttpClientHandler.DangerousAcceptAnyServerCertificateValidator;
```

The `!IsProduction()` exemption is a noise-reduction policy: it also covers Staging and custom environments. It does **not** establish that a bypass is safe in deployed non-production systems. Direct `IsStaging()` checks, custom environment names via `IsEnvironment(...)`, arbitrary flags, lookalike helper methods, and `IsDevelopment() || overrideFlag` are not inferred as exemptions. A guarded delegate declaration does not exempt a callback configured later in a deferred lambda/local function. Do not run production applications with their environment set to Development.

### Keep proxy debugging exceptions out of Release code

Certificate interception proxies sometimes require a deliberate bypass during debugging:

```csharp
#if DEBUG
handler.ServerCertificateCustomValidationCallback =
    HttpClientHandler.DangerousAcceptAnyServerCertificateValidator;
#endif
```

The rule ignores configuration that disappears when `DEBUG` is undefined, including nested directives and the `else` branch of `#if !DEBUG`. A Debug build alone does not disable the rule. `#if DEBUG || OTHER_SYMBOL` remains reportable when the other symbol keeps it active without `DEBUG`. Defining `DEBUG` inside the source file also keeps that code active and is not an exemption. This is a build-policy exception; ensure production builds do not define `DEBUG`.

### Test projects

DNA0020 is quiet by default when the evaluated project property `IsTestProject` is `true`. The analyzer package exposes this metadata automatically; the CLI uses reconstructed project markers by default, or evaluated metadata with `-p`, even without the analyzer package installed. Other rules remain enabled. Project/file names, test-looking namespaces, and references to test libraries do not determine this exemption.

To audit certificate bypasses in a test project, add a `.globalconfig` file:

```ini
is_global = true
dotnetarium_analyze_test_certificates = true
```

This opt-in restores ordinary DNA0020 detection in test projects; development, non-production and DEBUG-only exemptions still apply. For a fixture in a project without `IsTestProject=true`, use a scoped suppression below.

To constrain an exception to development **and** loopback requests while retaining validation elsewhere:

```csharp
handler.ServerCertificateCustomValidationCallback = (request, certificate, chain, errors) =>
{
    if (environment.IsDevelopment() && request.RequestUri?.IsLoopback == true)
        return true;

    return errors == SslPolicyErrors.None;
};
```

This is a deliberate exception to certificate authentication for those requests, not a secure replacement for trusting a certificate. The rule leaves this conditional callback quiet because it is not proven to accept every certificate.

### Keep validation or pinning

Callbacks that validate policy errors or explicitly pin a certificate are not treated as accept-all callbacks. For example, a pin can strengthen normal validation:

```csharp
handler.ServerCertificateCustomValidationCallback = (_, certificate, _, errors) =>
    errors == SslPolicyErrors.None &&
    certificate != null &&
    certificate.GetCertHashString(HashAlgorithmName.SHA256) == expectedCertificateHash;
```

A validator that throws to reject a certificate, or calls a helper that may do so, is also left quiet. The rule does not assume such helpers are safe; it declines to claim they accept everything.

### Suppress a deliberate invalid-certificate fixture narrowly

If accepting invalid certificates is the purpose of a test, suppress just its configuration:

```csharp
#pragma warning disable DNA0020 // Deliberate invalid-certificate integration fixture.
handler.ServerCertificateCustomValidationCallback =
    HttpClientHandler.DangerousAcceptAnyServerCertificateValidator;
#pragma warning restore DNA0020
```

Alternatively, limit an `.editorconfig` override to a dedicated test directory:

```ini
[tests/CertificateFixtures/**/*.cs]
dotnet_diagnostic.DNA0020.severity = none
```

Avoid disabling the rule for application code. `localhost`, loopback IPs, a fixed `BaseAddress`, and a test-like class/file name do not automatically suppress an unconditional bypass: handlers can be reused, globals affect other callers, and raw TLS callbacks do not reliably expose the destination.
